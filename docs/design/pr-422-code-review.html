Risk: high. Request changes.

Header parsing, the immutable registry swap, size bounds, and the RequiresProfile status are in decent shape. Play is not. Compatibility still treats a known executable plus the wrong INI as a known client, data patches match across GeneralsOnline QFEs, and a third-party replay profile is built pointing at the retail generals.exe. Several unit tests assert those behaviors as success.

What the PR actually ships

Replay Manager now reads GENREP headers, looks up exeCRC/iniCRC in an embedded crc-mapping.json (122-ish game clients), paints a compatibility badge, and can create plus launch a dedicated profile. Catalog refresh polls raw.githubusercontent.com/.../development/.../crc-mapping.json every 24 hours, with a local fallback file. Steam launch, profile messenger wiring, and HasCompatibleCatalogIdentity were widened so those replay profiles can start.

The PR description still talks about a GitHub Gist. The code does not. The live URL is the development branch of this repo.

Blockers

Blocker Exe-only CRC fallback is treated as a hit

SAGE replays are identified by the pair. TryGetEntry misses the pair, then still returns the ExeMap row and stamps Custom INI (...) with DataPatchManifestId = null. 

var normalized = NormalizeHex(exeCrc);
if (!string.IsNullOrEmpty(normalized) && state.ExeMap.TryGetValue(normalized, out var baseEntry))
{
    entry = baseEntry with
    {
        IniCrc = $"0x{NormalizeHex(iniCrc)}",
        DataPatchName = $"Custom INI (0x{NormalizeHex(iniCrc)})",
        DataPatchManifestId = null,
    };
    return true;
}

Every SuperHackers Zero Hour row in the committed catalog shares vanilla INI 0x76B251A3. A TSH weekly exe with a community or GO INI therefore becomes “matched TSH client, no patch required.” FindMatchingProfile then accepts any TSH profile of that version. Badge says Ready to Play. The replay desyncs or refuses to load.

CrcMappingRegistryTests locks this in: TryGetEntry("0x27533BB0", "0xDEADBEEF") must succeed. That is the wrong contract for replay playback.

Same-exe collisions in the catalog make ExeMap order-dependent. GeneralsOnline 0xB9DB8815 is both 082826_QFE1 (ini 0x81FB5632) and base 082826 (ini 0x5CB7992C). Pair lookup is fine. The fallback is not.

Blocker Third-party replay profiles point at the retail executable

ResolveReplayGameClientAsync takes the installation’s ZeroHourClient.ExecutablePath (Steam/EA generals.exe). If that is set, GetDefaultExecutableName never runs, so SuperHackers generalszh.exe is ignored. ResolveThirdPartyGameClientAsync then writes that retail path and working directory onto the new GameClient.

This PR also taught launch to trust that filename:

  • WorkspaceStrategyBase.UpdateWorkspaceInfo used to skip the filename fallback when a GameClient manifest existed. It now falls back whenever ExecutablePath is still empty, using Path.GetFileName(configuration.GameClient.ExecutablePath). A TSH workspace that still contains linked retail generals.exe will resolve to that file.
  • GameLauncher.ResolveAndValidateExecutablePath gained the same filename search inside the workspace before falling back to the profile path.

Create-profile tests for GO/TSH assert GameClientId only. The only ExecutablePath assertion is the retail path-from-directory case. Nobody checks that Play starts the acquired publisher binary.

Blocker Data patches match with no version check

Client matching at least AND-gates HasMatchingClientVersion. Data patches do not: 

return profile.EnabledContentIds?.Any(id =>
    string.Equals(id, dataPatchManifestId, StringComparison.OrdinalIgnoreCase) ||
    DependencyResolver.HasCompatibleCatalogIdentity(dataPatchManifestId, id)) == true;

HasCompatibleCatalogIdentity ignores segment 1 (user version). For patch type it then treats any two gamedata names as the same. So 1.828261.generalsonline.patch.gamedata matches 1.82826.generalsonline.patch.gamedata and also 1.60526....patch.gamedata.

The same helper is the new launch-validation fallback in ProfileLauncherFacade.ResolveManifestForValidationAsync: exact pool miss becomes “first pooled manifest with the same publisher and type.” That is load-bearing for every profile, not just replays.

There is no negative test for a wrong-week GO patch. The “version matches” third-party test sets both sides to 082826 while using catalog id 1.828261 (QFE1).

Blocker QFE vs base prefix match when Version is empty

HasMatchingVersionSegment treats two version segments as equal when the shorter is at least 5 chars, the lengths differ by at most 1, and one is a prefix of the other. 82826 vs 828261 is a hit. That is GeneralsOnline base vs QFE1.

The branch only runs when a Version string is missing on either side. Production GameClient.Version is often empty on older profiles. The test CreateProfileForReplayAsync_WhenCatalogIdDiffersFromPooledClientVariant_ResolvesPooledManifestIdAsync sets Version 082826 on a QFE1 catalog id and expects the pooled 1.82826.generalsonline.gameclient.60hz client. That is the bug, signed off.

DependencyResolverTests also requires 1.0828261.generalsonline.gameclient.zerohour ≡ 1.82826.generalsonline.gameclient.60hz. Fine for “any GO client satisfies a type dependency.” Unsafe as a CRC stand-in.

Warnings

Warning Installation pick ignores catalog publisher

Steam ZH exe CRC is 0x401D89EA. Retail/EA in this catalog is 0xDA2B4B18 (and a second EA row that reuses the Steam CRC with a different SHA-256). ResolveInstallation is FirstOrDefault with HasZeroHour. A machine with Origin and Steam can build an EA profile for a Steam replay. Pair lookup did the hard work, then create threw it away.

Warning Null GameClient is treated as compatible

if (profile.GameClient == null)
{
    // Profile without GameClient (e.g. In mocks/test harnesses) is assumed valid
    return true;
}

That comment is written for the test harness. LaunchReplayAsync_WhenMatchingProfileExists depends on it. A persisted profile with a dropped client still launches.

Warning Replay Play cleans other profiles’ user data

LaunchReplayAsync calls the facade with skipUserDataCleanup: false. skipCleanup: true is the adopt-maps path. False means maps linked by the previously active profile are not adopted, then lingering profiles are deactivated. Custom-map replays can lose the map they need. Dedicated replay Play should pass true.

Warning Catalog and generator do not measure SAGE iniCRC

  • Without --inspect-binaries, TSH ZH INI is hardcoded 0x76B251A3 and GO is 0x5CB7992C. Empty exeCrc rows are skipped, so a crawl without inspect is a no-op.
  • With inspect, INI is zlib.crc32 of mapcachego.ini / generals.ini. That is not the engine overlay CRC stored in the replay header.
  • Committed catalog: 49/49 TSH ZH INIs are vanilla 0x76B251A3. 19/23 GO INIs are the default 0x5CB7992C.
  • Steam last-write wins on duplicate pairs, so the EA row at 0x401D89EA/0x76B251A3 is unreachable. Those two rows also disagree on SHA-256 while claiming to be the same binary.
  • Two “Vanilla 1.04 INI” retail rows share a manifest id and differ only by INI (0xFEAAE3F3 vs 0x76B251A3). RegisterEntry replaces by ManifestId and would collapse them.

Warning Steam replay profiles still install the proxy

BuildReplayProfileRequest sets UseSteamLaunch when the install is Steam. Create now persists that flag. Play then replaces generals.exe with the proxy and ForceRecreates the workspace. That is existing Steam-launch machinery, now on the “watch a replay” button. Surprising, and it multiplies the wrong-exe bug above.

Related launcher change: pre-launch cleanup now also runs when a generals.exe.ghbak exists on a non-Steam launch, and failure is ignored unless isSteamLaunch. A leftover proxy can stay in the install.

Warning Header parser still swallows Exception

ParseHeaderAsync(Stream) uses catch (Exception ex) when (ex is not OperationCanceledException). Repo rule CS-R1008. File-path overload is correctly limited to IOException / UnauthorizedAccessException. Non-seekable streams also skip the 10 MB cap.

Warning UI and docs nits that will bite

  • Compatibility dots are literal ● in ReplayManagerView.axaml. Styling guide wants PathIcon or a theme brush, not Unicode glyphs.
  • Grid Play / Profile / Setup have no IsEnabled against IsBusy. Double-click races two launches.
  • Receive(ProfileDeletedMessage) mutates replay collections on the sender thread, then posts a reload. Launcher VM marshals the same messages with RunOnUi.
  • HasSelectedZips hardcodes ".zip" despite ReplayManagerConstants.ZipFileExtension.
  • IReplayDirectoryService.DeleteReplaysAsync says Recycle Bin. Implementation is File.Delete.
  • Play launches the profile. It does not pass the replay filename to the process. The user still picks the file in-game. The button copy implies otherwise.
  • AcquireGeneralsOnlineMapPacksAsync acquires every GO map pack the search returns, with no version pin.
  • PR includes a 1-line AGENTS.md GitNexus bump. Leave that off the feature branch.

What I would change before merge

  1. Make TryGetEntry pair-only. Keep TryGetEntryByExeCrc for diagnostics. Custom INI is Orphaned, not Ready to Play.
  2. Resolve TSH/GO executable and working directory from the acquired client manifest, not from the Steam/EA install. Stop the filename fallback from selecting generals.exe when the profile’s publisher is not retail.
  3. Require version (and GO variant) equality for data-patch identity. Do not reuse HasCompatibleCatalogIdentity as CRC equality in replay matching or launch validation.
  4. Drop the prefix rule in HasMatchingVersionSegment, or require an exact segment. Fix the tests that want QFE1 to resolve to base 60 Hz.
  5. Pick the installation whose publisher matches the catalog row. Null GameClient is not compatible.
  6. Pass skipUserDataCleanup: true on replay launch. Strongly consider UseSteamLaunch = false on replay-created profiles.
  7. Stop generating catalog INIs from defaults / zlib of loose ini files. Measure whatever the engine writes into the replay header, or leave INI empty and do not match.

Recommendation

Request changes. Builds and Core tests are green. That is the problem: the suite agrees with the unsafe matching. I would not merge until pair-only CRC lookup, publisher-client binaries, and version-strict patches are the behavior under test.

Prior bot comments (Greptile version-agnostic clients, Qodo empty registry, Kilo size cap) are partly addressed. The remaining defects are in matching and launch, which those passes only grazed.
